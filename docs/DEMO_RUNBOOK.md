# บทเดโม 5–7 นาที

ภาพจากการรันบน PC: [หน้าประเมินและค่าเซนเซอร์](images/dashboard-pc.png) /
[สรุปภาษาไทยและประวัติ](images/dashboard-summary-pc.png)
บนจอกว้างจะแสดงสามคอลัมน์ ส่วนหน้าต่างแคบจะเรียงสรุปไว้ด้านล่าง

## เตรียมก่อนนำเสนอ

- ใช้ release ที่ผ่าน `pi_check.py --release .` แล้ว เปิด dashboard บน Pi
- template เป็นเดโมพื้นฐานที่ต้องทำงานได้เสมอ; เปิด LLM เฉพาะเมื่อทดสอบจริงแล้ว
- ใช้ HDMI/display ของ Pi เพื่อแสดงการตัด Wi-Fi/LAN ให้ผู้ชมเห็นได้
- กดเริ่มใหม่ก่อนเริ่ม; snapshot ใน demo ถูกจัดสลับ normal/alert จาก test set
- บอกว่าเป็น **CSV replay ของ AI4I สังเคราะห์** และเป็น snapshot classification
  ไม่ใช่การวัดปั๊มจริง/ทำนายเวลาที่จะเสีย

## ฉากที่ 1 — เห็นเส้นทางข้อมูล (1 นาที)

ชี้แถบ 4 ขั้นตอน: รับข้อมูล → ML → ตัวกลาง Python → สรุปไทย
แนะนำสามคอลัมน์: ค่าที่วัด / ผลโมเดล / ข้อความภาษาไทย
ชี้แหล่งข้อมูล, โหมด template หรือ LLM และเครื่องที่กำลังรัน

## ฉากที่ 2 — อ่าน snapshot ปกติ (1 นาที)

กด **อ่านแถวถัดไป** แถวแรกใน release AI4I โดยทั่วไปเป็นผล normal
แสดงชนิดผลิตภัณฑ์ อุณหภูมิ Kelvin, RPM, torque และ wear
อธิบายว่า model คำนวณ score แล้วเทียบ threshold ที่เก็บจาก validation
ชี้ว่า score ไม่ใช่ความน่าจะเป็นเสียที่ผ่าน calibration

## ฉากที่ 3 — เปลี่ยนเป็นสถานะเตือน (1 นาที)

กดอ่านอีกแถว ผล alert ใช้สี amber พร้อมข้อความควรตรวจบำรุงรักษา
เปิดส่วน **ดูข้อมูลที่ตัวกลางจัดให้ระบบสรุป** ให้เห็น status, score, threshold,
readings และข้อจำกัด ตัวกลางทำหน้าที่จัดข้อเท็จจริงและควบคุมความถูกต้องของข้อความ
LLM ไม่ได้เปลี่ยนผลจำแนกหรือสร้างตัวเลขใหม่

ถ้า release มีคลาสที่โมเดลทำนายเพียงแบบเดียว สคริปต์จะไม่สร้าง alert ปลอม
ตรวจ `demo_provenance.json` และเลือกอธิบายข้อจำกัดนั้น (โดยเฉพาะชุดปั๊มเดิม)

## ฉากที่ 4 — LLM และ fallback (1–2 นาที)

ถ้าใช้ template: ชี้ `summary_method=template` และบอกตรง ๆ ว่ายังไม่เรียก LLM
ถ้ามี LLM จริง: ML แสดงผลก่อนและขึ้นว่ารอ LLM จากนั้นต้องเห็น
`local_llm_validated` พร้อมเวลาที่ใช้ จึงนับว่า GGUF ทำงานสำเร็จ

LLM ปัจจุบันเลือกประโยค A/B ตามข้อเท็จจริง ไม่ใช่ chatbot วินิจฉัยอิสระ
สาธิต runtime failure ตาม PI_HANDOFF ข้อ 4 เพื่อให้เห็น `template_llm_unavailable`
และสรุปไทยยังอยู่ครบ ค่า status/score ไม่เปลี่ยน ถ้าไม่มี runtime พร้อมไม่ต้องจำลอง
ผลว่าเป็น LLM จริง ให้บอกว่า fallback ผ่าน automated tests ส่วน GGUF รอทดสอบ

## ฉากที่ 5 — เล่นต่อและตรวจทรัพยากร (1 นาที)

กด **เล่นอัตโนมัติ** แสดงประวัติและกราฟคะแนนตามแถว จากนั้น **หยุดพัก**
คำสั่งหยุดมีผลกับแถวถัดไป แถวปัจจุบันอาจรอ LLM ไม่เกิน 30 วินาที
ชี้ RAM โปรแกรม/RAM ระบบ/อุณหภูมิที่อ่านได้ และบันทึกผล JSON
แสดงไฟล์ benchmark จาก Pi แยก เพราะค่าหน้า dashboard เป็นค่าขณะนั้น ไม่ใช่ peak

## คำตอบเมื่อถูกถาม

| คำถาม | คำตอบ |
| --- | --- |
| ต้องมีอินเทอร์เน็ตไหม | ตอนเตรียม dependency/โมเดลต้องมี ตอน inference/template/LLM ไม่ใช้ |
| ML กับ LLM ใครตัดสินเครื่องเสีย | ML + threshold; ตัวกลางจัด facts; LLM เลือกข้อความที่ตรวจสอบได้ |
| Accuracy 99% แปลว่าจับเครื่องเสียได้เกือบทั้งหมดไหม | ไม่ใช่ ผลหลัก recall เครื่องเสีย 71.79%, F1 78.87%; ต้องอ่านหลาย metric |
| ใช้กับปั๊มจริงได้เลยไหม | ยังไม่ได้ยืนยัน ต้องมี sensor schema/หน่วย/label จากปั๊มจริงและประเมินใหม่ |
| ทำไมไม่ใช้ชุดปั๊มเดิม | ทดสอบแล้วใกล้ baseline จึงเก็บไว้แสดงข้อจำกัด และใช้ AI4I สาธิต pipeline |
| กราฟทำนายอนาคตไหม | เป็นคะแนนของ snapshot replay ตามลำดับสาธิต ไม่มีเวลาเสีย/RUL |
| ต่อ live sensor ตรงไหน | เพิ่ม adapter ส่ง snapshot เข้าตัวกลางหลังตกลง schema; ตอนนี้มีเฉพาะ CSV |
